# Anonymizer - lab deployment on a Docker VM (Proxmox)

This guide assumes a **completely fresh** install, on a VM that has never run this project before. Every step exists because a real from-scratch test tripped over it — follow them in order, without skipping any, even the ones that look obvious.

## 0. Proxmox VM prerequisites — check BEFORE starting anything

**VM CPU type.** If the VM is configured with a generic processor type (`qemu64`, the default on many Proxmox setups), some services (Keycloak in particular) crash on startup with a cryptic error:

```
Fatal glibc error: CPU does not support x86-64-v2
```

This isn't an application bug — the Docker image targets a CPU instruction set (x86-64-v2) that the generic CPU type doesn't expose inside the VM, even if the host's physical CPU supports it perfectly well.

**Fix, in the Proxmox interface, before continuing:**

1. Shut down the VM (not just restart the containers).
2. VM → **Hardware** → **Processor** → **Edit**.
3. Type: **`host`** (simplest, inherits the physical CPU directly) — or an explicit v2-compatible type (`x86-64-v2-AES`) if you plan to migrate the VM to a different host later.
4. Restart the VM.

Once restarted, verify before even installing Docker:

```bash
grep -o 'sse4_2' /proc/cpuinfo | head -1
```

If `sse4_2` shows up, you're good.

## 1. Clone the repository

```bash
ssh debian@<vm-ip>
git clone https://github.com/EpicFail20/obfusk8.git
cd obfusk8
```

## 2. Add the domain to `/etc/hosts` (client machine, not the VM)

```
<vm-ip>  anonymiseur.lab.local
```

This line goes in the hosts file of **your local machine** (the one with the browser) — not the VM's.

## 3. Generate the secrets — BEFORE any `docker compose up`

```bash
chmod +x generate-secrets.sh
./generate-secrets.sh
```

This script creates the `secrets/` folder with the right restrictive permissions (700/600) and automatically generates two random secrets (cookie secret, internal gateway secret). It also asks you to type in two values manually — here's how to answer each one **during a first-time install**, when the Keycloak OIDC client doesn't exist yet:

- **`Keycloak admin password`**: choose and type the password you want the Keycloak admin account to have — you're the one defining it, Keycloak doesn't exist yet so there's nothing to retrieve.
- **`OAUTH2_PROXY_CLIENT_SECRET`**: at this point you don't have it yet (it will be generated by Keycloak in step 5). Type any placeholder value (e.g. `placeholder-to-replace`) — it will be overwritten manually later, **with no need to rerun the whole script**.

⚠️ **Important: run this script before the very first `docker compose up`, never after a failed attempt.** If Docker has already tried to start the services before this script created `secrets/`, the folder may end up owned by `root`, causing a `Permission denied` when generating. If that happens:

```bash
sudo chown -R $(whoami):$(whoami) ./secrets ./traefik/dynamic
./generate-secrets.sh --force
```

Check that the cookie secret is exactly 32 bytes before continuing (otherwise `oauth2-proxy` will refuse to start with `cookie_secret must be 16, 24, or 32 bytes`):

```bash
wc -c < ./secrets/oauth2_cookie_secret.txt   # should show 32
```

## 4. Copy and fill in `.env`

```bash
cp .env.example .env
```

Edit `.env` — at this stage, only `APP_DOMAIN` needs a real value (`anonymiseur.lab.local`). Everything else can stay at its default for a first test.

## 5. Start Keycloak alone, configure it, retrieve the real client secret

```bash
docker compose up -d keycloak
docker compose logs -f keycloak
```

Wait for the logs to settle (or check `docker compose ps` — Keycloak should reach the `healthy` state, which can take 1 to 2 minutes on first startup).

- Open `http://<vm-ip>:8081` — log in with `admin` / the password you typed in step 3.
- Create a `lab` realm.
- Create a `SG-Anonymiseur-Utilisateurs` group.
- Create a confidential OIDC client `anonymiseur-app`, with redirect URI:
  `https://anonymiseur.lab.local/oauth2/callback`
- Add a "Group Membership" mapper → `groups` claim.
- Create 1-2 test users, add them to the group.
- **Retrieve the real client secret** generated by Keycloak (client's *Credentials* tab).

**Now replace the placeholder value** typed in step 3, directly, without rerunning the whole script (which would needlessly regenerate the cookie secret and force a restart of already-stable containers):

```bash
printf '%s' '<real-secret-copied-from-keycloak>' > ./secrets/oauth2_client_secret.txt
chmod 600 ./secrets/oauth2_client_secret.txt
```

## 6. Start the rest of the stack

```bash
docker compose up -d --build --scale presidio-analyzer=2 --scale presidio-anonymizer=1
docker compose ps
```

Along the way, `app` now automatically waits for a small dedicated service (`fix-app-dirs-perms`) to fix the permissions of its data folders before starting — no more manual `chown` needed before first launch, regardless of the initial state of those folders on the host.

(2 replicas are enough for a functional test; scale up to 6/2 only for the 50-concurrent-user load test — sizing already covered elsewhere: 12-16 vCPU / 24-32 GB in that case.)

If published images are already referenced in `docker-compose.yml` (`image: ghcr.io/...`), you can run `docker compose pull` first to speed things up — keeping `--build` alongside it is harmless either way, it does nothing more than a local build if an up-to-date local image already exists.

**Check that everything stays stable, not just started:**

```bash
docker compose ps
```

Every service should show `Up`/`Running`/`Healthy`, with no restart counter (`Restarting (1)...`) that keeps increasing. If `app` or `oauth2-proxy` keeps restarting, check the logs (`docker compose logs <service> --tail=50`) — the most common causes at this stage are listed in the troubleshooting table below.

## 7. Verify and log in

```bash
docker compose logs -f app
docker compose logs -f oauth2-proxy
```

Open **`https://anonymiseur.lab.local`** (make sure it's `https`, not `http` — Traefik only serves the application over HTTPS). Your browser will show a certificate warning (expected, self-signed certificate in the lab): accept it to continue. You should then be redirected to Keycloak, log in with a test user from the group, and land on the app.

## Troubleshooting — errors hit during a real test, and their exact cause

| Symptom | Cause | Fix |
|---|---|---|
| `Fatal glibc error: CPU does not support x86-64-v2` (Keycloak logs) | VM's CPU type too generic | Step 0 — `host` type in Proxmox |
| `PermissionError: ... '/data/audit/audit.log'` (app logs) | Host folder (`/var/log/anonymiseur-audit`, mounted at `/data/audit`) created by Docker as root before the application user (UID 1000) can write to it | Fixed automatically since the `fix-app-dirs-perms` service was added — if you still see this error, check that it completed successfully: `docker compose ps fix-app-dirs-perms` should show `Exited (0)` |
| `cookie_secret must be 16, 24, or 32 bytes... but is N bytes` (oauth2-proxy logs, on a loop) | Invalid secret file, or generated with an incompatible encoding | Step 3 — regenerate with `generate-secrets.sh --force` after fixing `./secrets` permissions, check `wc -c` = 32 |
| `./generate-secrets.sh: ... Permission denied` writing to `secrets/` | The `secrets/` folder is owned by `root` (created by a `docker compose up` run before the script) | `sudo chown -R $(whoami):$(whoami) ./secrets ./traefik/dynamic` then rerun with `--force` |
| `oauth2-proxy` keeps restarting after the "cookie secret" issue is fixed | Client secret still set to its temporary/placeholder value, Keycloak rejects it | Step 5 — overwrite `secrets/oauth2_client_secret.txt` with the real value retrieved from Keycloak |
| Page unreachable at `http://anonymiseur.lab.local` | Traefik only serves over HTTPS | Use `https://` |
| `git clone`/`docker pull` asks for login even though the repo/package is supposed to be public | The visibility change wasn't confirmed all the way through on GitHub's side (confirmation dialog closed before the final button) | Recheck `Settings → Danger Zone` (repo) or `Package settings` (package), redo the confirmation all the way to the end |

## Switching to Entra ID later

In `oauth2-proxy.cfg`, replace `provider = "oidc"` with `provider = "entra-id"` and point `oidc_issuer_url` to `https://login.microsoftonline.com/<tenant-id>/v2.0`, with the real Entra `client_id`/`client_secret` (the latter replaces the content of `secrets/oauth2_client_secret.txt`, same mechanics as step 5). No other file changes.
