# Anonymizer - lab deployment on a Docker VM (Proxmox)

This guide assumes a **completely fresh** install, on a VM that has never run this project before. Every step exists because a real from-scratch test tripped over it — follow them in order, without skipping any, even the ones that look obvious.

## 0. Proxmox VM prerequisites — check BEFORE starting anything

**VM CPU type.** If the VM is configured with a generic processor type (`qemu64`, the default on many Proxmox setups, or inherited from a cloned template), some services (Keycloak in particular) crash on startup with a cryptic error:

```
Fatal glibc error: CPU does not support x86-64-v2
```

This isn't an application bug — the Docker image targets a CPU instruction set (x86-64-v2) that the generic CPU type doesn't expose inside the VM, even if the host's physical CPU supports it perfectly well.

**Fix, in the Proxmox interface, before continuing:**

1. Shut down the VM (not just restart the containers).
2. VM → **Hardware** → **Processor** → **Edit**.
3. Type: **`host`** (simplest, inherits the physical CPU directly) — or an explicit v2-compatible type (`x86-64-v2-AES`) if you plan to migrate the VM to a different host later.
4. Restart the VM.

Once restarted, verify before even installing Docker:

```bash
grep -o 'sse4_2' /proc/cpuinfo | head -1
```

If `sse4_2` shows up, you're good.

## 1. Clone the repository

```bash
ssh debian@<vm-ip>
git clone https://github.com/EpicFail20/obfusk8.git
cd obfusk8
```

⚠️ The **folder name matters**: Docker Compose automatically names its networks `<folder-name>_<network-name>`. If you clone anywhere other than a folder named `obfusk8` (say, a manual rename, or an old project name like `anonymiseur`), some Traefik labels in this file (`traefik.docker.network=obfusk8_app-internal`) will no longer match the real generated network name, and the application will stay unreachable (a generic 404) despite otherwise-correct configuration — this actually happened in the lab, see the troubleshooting table. If you must use a different folder name, update those two labels accordingly.

## 2. Add both domains to `/etc/hosts` (client machine, not the VM)

**Two entries are needed**, not just one — easy to miss, since only the first one is obviously referenced in later steps:

```
<vm-ip>  anonymiseur.lab.local
<vm-ip>  keycloak.lab.local
```

`keycloak.lab.local` is needed starting at step 5: Keycloak always redirects to this hostname (hardcoded in `docker-compose.yml` via `KC_HOSTNAME`), even when accessed via the IP or `localhost`. Without this entry, your browser follows the redirect to a name it can't resolve and the page just hangs, with no clear error.

These two lines go in the hosts file of **your local machine** (the one with the browser) — not the VM's.

## 3. Generate the secrets — BEFORE any `docker compose up`

```bash
chmod +x generate-secrets.sh
./generate-secrets.sh
```

This script creates the `secrets/` folder with the right permissions and automatically generates two random secrets (cookie secret, internal Traefik gateway secret). It also asks you to type in two values manually — here's how to answer each one **during a first-time install**, when the Keycloak OIDC client doesn't exist yet:

- **`Keycloak admin password`**: choose and type the password you want the Keycloak admin account to have — you're the one defining it, Keycloak doesn't exist yet so there's nothing to retrieve.
- **`OAUTH2_PROXY_CLIENT_SECRET`**: at this point you don't have it yet (it will be generated by Keycloak in step 5). Type any placeholder value (e.g. `placeholder-to-replace`) — it will be overwritten manually later, **with no need to rerun the whole script**.

⚠️ **Important: run this script before the very first `docker compose up`, never after a failed attempt.** If Docker has already tried to start the services before this script created `secrets/` or `traefik/dynamic/`, those folders may end up owned by `root`, causing a `Permission denied` when generating. If that happens:

```bash
sudo chown -R $(whoami):$(whoami) ./secrets ./traefik/dynamic
./generate-secrets.sh --force
```

Check that the cookie secret is exactly 32 bytes before continuing:

```bash
wc -c < ./secrets/oauth2_cookie_secret.txt   # should show 32
```

## 4. Copy and fill in `.env`

```bash
cp env.en.example .env
```

Edit `.env` — `APP_DOMAIN` and `OAUTH2_PROXY_CLIENT_ID` are the two values to change first; the others (anti-abuse caps `MAX_*`, `FILE_TTL_SECONDS`...) have safe defaults, adjust them later if needed.

⚠️ **Never add `OAUTH2_PROXY_CLIENT_SECRET` or `OAUTH2_PROXY_COOKIE_SECRET` to this file**, even temporarily, even "just to test quickly." Both values go exclusively through the Docker secrets generated in step 3 (`OAUTH2_PROXY_CLIENT_SECRET_FILE` / `OAUTH2_PROXY_COOKIE_SECRET_FILE`, already wired up in `docker-compose.yml`). If either variable shows up in `.env`, `oauth2-proxy` gives it priority over the matching Docker secret and fails at startup with an error that looks like it comes from nowhere. **This trap was hit twice, separately, in the lab** — once on the cookie secret (`cookie_secret must be 16, 24, or 32 bytes... but is 51 bytes`), once on the client secret (`unauthorized_client` / `invalid_client_credentials` on Keycloak's side) — 51 being precisely the length of an old `.env.example` placeholder string, not that of a real secret. If you see either error, **check `.env` first, before any other lead**.

⚠️ **History: `redirect_url` used to be hardcoded in `oauth2-proxy.cfg`, independent of `.env`** — that was the case early in this project and it caused a real blocker during a domain change in the lab. That's no longer the case: `redirect_url` is now derived from `APP_DOMAIN` via the `OAUTH2_PROXY_REDIRECT_URL` environment variable in `docker-compose.yml`, same as everything else. `APP_DOMAIN` in `.env` is therefore the single source of truth to change — see [Changing the domain later](#changing-the-domain-later) for the full checklist (shorter than it used to be).

## 5. Start Keycloak alone and configure it

```bash
docker compose up -d keycloak
docker compose logs -f keycloak
```

Wait for the logs to show a line like `Keycloak ... started in ...s. Listening on: http://0.0.0.0:8080` (or check `docker compose ps` — Keycloak should reach the `healthy` state, which can take 1 to 2 minutes on first startup). The usual `WARN` lines (a minor JDBC leak from the dev H2 database, the "development mode" reminder) are normal under `start-dev` and don't indicate any failure.

Open **`http://keycloak.lab.local:8080`** — not `:8081` (an error present in an earlier version of this guide), and use `keycloak.lab.local`, not the IP directly (you'd get redirected there anyway, so start from the right name).

Log in with `admin` / the password typed in step 3.

### 5.1 Create the realm

1. Top left, click the realm selector (shows "master" by default).
2. **Create realm**.
3. Realm name: `lab` (exactly, lowercase).
4. **Create**. Check that the selector now shows "lab" before continuing — every following step must happen inside this realm, not "master".

### 5.2 Create the group

1. Left menu → **Groups** → **Create group**.
2. Name: `SG-Anonymiseur-Utilisateurs` (match the casing).
3. **Create**.

### 5.3 Create the confidential OIDC client

1. Left menu → **Clients** → **Create client**.
2. *General settings* screen: Client type stays `OpenID Connect`. Client ID: `anonymiseur-app`. **Next**.
3. *Capability config* screen: **turn on the `Client authentication` toggle** (off by default — this, and only this, is what makes the client confidential rather than public; without it, no *Credentials* tab will show up afterward and `oauth2-proxy` will have no client secret to use). Under *Authentication flow*, leave `Standard flow` checked. **Next**.
4. *Login settings* screen: *Valid redirect URIs*: `https://anonymiseur.lab.local/oauth2/callback` (exactly, adjust to whatever domain you actually use). **Save**.
5. Once the client is created, go to the **Credentials** tab (only shows up because *Client authentication* was enabled) → copy the **Client secret** value.

### 5.4 Add the "Group Membership" mapper

1. On the client's page, **Client scopes** tab.
2. Click the `anonymiseur-app-dedicated` row (the "Dedicated" scope specific to this client).
3. **Add mapper** → **By configuration**.
4. Type: **Group Membership**.
5. *Name*: anything (e.g. `groups`). *Token Claim Name*: **`groups`** exactly — this is the precise name the application will look for in the token. *Full group path*: **On** (important — `oauth2-proxy.cfg` references the group by its full path, `/SG-Anonymiseur-Utilisateurs`, slash included; with *Off*, the comparison would fail silently). Check that *Add to ID token* and *Add to access token* are both enabled (they are by default).
6. **Save**.

### 5.5 Create and assign the "groups" Client Scope

⚠️ A required step, distinct from 5.4, and easy not to expect: `oauth2-proxy.cfg` contains `allowed_groups = ["/SG-Anonymiseur-Utilisateurs"]`, which makes `oauth2-proxy` explicitly request an OAuth scope named **`groups`** during login. Without this step, Keycloak rejects the request with `invalid_scope: Invalid scopes: openid email profile groups` — the mapper from step 5.4 alone isn't enough; that scope name also needs to exist and be assigned to the client.

1. Left menu (not inside the client's page) → **Client scopes** → **Create client scope**.
2. Name: `groups` (exactly). Protocol: `openid-connect`. **Save**.
3. On the newly created scope's page, **Mappers** tab → **Add mapper** → **By configuration** → **Group Membership**. Same settings as step 5.4 (*Token Claim Name* = `groups`, *Full group path*: On). **Save**.
4. Go back to **Clients** → `anonymiseur-app` → **Client scopes** tab (the client's own this time) → **Add client scope** → check `groups` → assign it as **Default** (not *Optional*).

### 5.6 Create one or two test users

1. Left menu → **Users** → **Add user**. Username: `testuser1`. **Create**.
2. **Details** tab of their profile → turn on **Email verified**. If this stays unchecked, `oauth2-proxy` refuses to complete the login with a `500` error (`email in id_token isn't verified`), even after an otherwise successful Keycloak authentication.
3. **Credentials** tab → **Set password** → type a password → turn off *Temporary* (otherwise Keycloak will force a password change on first login) → **Save**.
4. **Groups** tab → **Join Group** → check `SG-Anonymiseur-Utilisateurs` → **Join**. Without this step, the token will never carry the right group, even with a valid password.
5. (Optional) Repeat for a second user, skipping the *Join Group* step this time, if you want to verify that access is correctly denied to someone outside the group.

### 5.7 Save the real client secret

Now replace the placeholder value typed in step 3, directly, without rerunning the whole script (which would needlessly regenerate the cookie secret and force a restart of already-stable containers):

```bash
printf '%s' '<real-secret-copied-from-keycloak>' > ./secrets/oauth2_client_secret.txt
chmod 644 ./secrets/oauth2_client_secret.txt
docker compose up -d --force-recreate oauth2-proxy
```

`644`, not `600`: containers like `oauth2-proxy` run as their own non-root user, whose UID generally doesn't match your VM account's — a `600` file would be unreadable to them (see troubleshooting below). `--force-recreate` isn't optional: a plain restart doesn't reread the secret file, Docker mounts it at container creation time.

## 6. Start the rest of the stack

```bash
docker compose up -d --build --scale presidio-analyzer=2 --scale presidio-anonymizer=1
docker compose ps
```

`app` automatically waits for a dedicated service (`fix-app-dirs-perms`) to fix its data folder permissions before starting — no manual step needed for that.

(2 replicas are enough for a functional test; scale up to 6/2 only for the 50-concurrent-user load test — sizing already covered elsewhere: 12-16 vCPU / 24-32 GB in that case.)

If published images are already referenced in `docker-compose.yml` (`image: ghcr.io/...`), you can run `docker compose pull` first to speed things up — keeping `--build` alongside it is harmless either way.

**Check that everything stays stable, not just started:**

```bash
docker compose ps
```

Every service should show `Up`/`Running`/`Healthy`, with no restart counter (`Restarting (1)...`) that keeps increasing.

## 7. Verify and log in

```bash
docker compose logs -f app
docker compose logs -f oauth2-proxy
```

Open **`https://anonymiseur.lab.local`** (make sure it's `https`, not `http`). Your browser will show a certificate warning (expected, self-signed certificate in the lab): accept it to continue. You should then be redirected to Keycloak, log in with a test user from the group, and land on the app.

## Changing the domain later

If `APP_DOMAIN` needs to change after a working first install (testing with a different name, moving from one lab to another), **four separate places** need updating — changing only `.env` leaves the application unreachable with a `404` or a broken authentication flow:

1. **`.env`**: new `APP_DOMAIN` value.
2. **Recreate the affected containers**, so Traefik labels (resolved at creation, not continuously) and `oauth2-proxy` (whose `OAUTH2_PROXY_REDIRECT_URL` is also derived from `APP_DOMAIN`) pick up the change:
   ```bash
   docker compose up -d --force-recreate traefik app oauth2-proxy
   ```
3. **`/etc/hosts`** on the client: replace the old main-domain entry with the new one (`keycloak.lab.local` doesn't change, it's independent of `APP_DOMAIN`).
4. **Keycloak** → **Clients** → `anonymiseur-app` → **Settings** → *Valid redirect URIs*: replace the old domain with the new one. This is the only step left that's manual outside of `.env` — Keycloak can't be driven from `docker-compose.yml`.

`oauth2-proxy.cfg` no longer needs touching: `redirect_url` is intentionally absent from it, replaced by `OAUTH2_PROXY_REDIRECT_URL=https://${APP_DOMAIN}/oauth2/callback` in `oauth2-proxy`'s `environment:` block (environment variables take priority over this `.cfg` file, as already explained for `client_id` in its own comments).

If the project's folder name also changes (see the warning in step 1), the `traefik.docker.network=obfusk8_app-internal` labels in `docker-compose.yml` need updating too, with the new folder name.

## Troubleshooting — errors hit during a real test, and their exact cause

| Symptom | Cause | Fix |
|---|---|---|
| `Fatal glibc error: CPU does not support x86-64-v2` (Keycloak logs) | VM's CPU type too generic | Step 0 — `host` type in Proxmox |
| Page hangs with no clear error when opening the Keycloak console | `keycloak.lab.local` missing from the client's `/etc/hosts`; Keycloak always redirects to that name (`KC_HOSTNAME`) | Step 2 — add both entries, not just one |
| Keycloak console unreachable on port 8081 | The actual mapped port is 8080 (an error in an earlier version of this guide) | Use `http://keycloak.lab.local:8080` |
| `PermissionError: ... '/data/audit/audit.log'` (app logs) | Host folder created by Docker as root before the application user (UID 1000) can write to it | Fixed automatically by the `fix-app-dirs-perms` service — if it still happens, check `docker compose ps fix-app-dirs-perms` (should show `Exited (0)`) |
| `cookie_secret must be 16, 24, or 32 bytes... but is 51 bytes` (oauth2-proxy, on a loop, **persists even after regenerating and verifying the file is 32 bytes**) | An `OAUTH2_PROXY_COOKIE_SECRET` line is sitting in `.env` and takes priority over the Docker secret — 51 is the length of the placeholder text, not a real secret | Step 4 — remove any `OAUTH2_PROXY_*_SECRET` line from `.env`; `docker compose up -d --force-recreate oauth2-proxy` |
| `unauthorized_client` then `invalid_client_credentials` (Keycloak logs), **despite a verified-correct `secrets/oauth2_client_secret.txt`** | Same bug as above, on `OAUTH2_PROXY_CLIENT_SECRET` this time — a leftover line in `.env` takes priority over the Docker secret | Step 4 — check `grep -i client_secret .env` (should be empty) and `docker compose config \| grep CLIENT_SECRET` (only one `_FILE` line should appear) |
| `could not read cookie secret file: /run/secrets/oauth2_cookie_secret` | Secret file is `600`, unreadable by the non-root UID of the `oauth2-proxy` container (different from your VM account's) | `chmod 644` on the files under `./secrets/` (already the default once `generate-secrets.sh` has been regenerated after this fix) |
| `./generate-secrets.sh: ... Permission denied` writing to `secrets/` or `traefik/dynamic/` | The folder is owned by `root` (created by a `docker compose up` run before the script) | `sudo chown -R $(whoami):$(whoami) ./secrets ./traefik/dynamic` then rerun with `--force` |
| A secret fix seems to have no effect even though the host file checks out fine | The container in question was never recreated — a plain restart doesn't reread the file, Docker copies/mounts the secret at container creation time | Always use `docker compose up -d --force-recreate <service>` after changing a secret file |
| `Cannot start the provider *file.Provider: ... /etc/traefik/dynamic: permission denied` (Traefik logs), followed by `middleware "gateway-secret@file" does not exist` on **every** `app` router | `traefik/dynamic` folder is `700` (via `umask 077` in `generate-secrets.sh`), unreadable by Traefik's non-root UID — breaks the entire file provider, taking down every router that depends on the `gateway-secret@file` middleware | `chmod 755 ./traefik/dynamic && chmod 644 ./traefik/dynamic/gateway-secret.yml`, then `docker compose up -d --force-recreate traefik` |
| `404 page not found` (raw Traefik response) on the main domain, even though `docker compose config \| grep "app.rule"` confirms a correct rule | `traefik.docker.network=...` label pointing to a stale network name (e.g. a leftover from an old project name) — Traefik matches the rule but can't find the target container on the network it's told to use | Check `docker network ls`, fix the label to match `<current-folder-name>_app-internal`, then `docker compose up -d --force-recreate traefik app oauth2-proxy` |
| Keycloak shows `Invalid parameter: redirect_uri`, with the old domain visible in the URL | The Keycloak client's *Valid redirect URIs* wasn't updated after an `APP_DOMAIN` change | See [Changing the domain later](#changing-the-domain-later), point 4 |
| `invalid_scope: Invalid scopes: openid email profile groups` (Keycloak, on the login screen) | `oauth2-proxy.cfg` requests a `groups` scope (via `allowed_groups`) that doesn't exist as a Keycloak Client Scope | Step 5.5 — create and assign the `groups` Client Scope |
| `500 Internal Server Error` / `email in id_token isn't verified` after an otherwise successful Keycloak login | *Email verified* unchecked on the user | Step 5.6 — check *Email verified* on the user's profile |
| Page unreachable at `http://anonymiseur.lab.local` | Traefik only serves over HTTPS | Use `https://` |
| `git clone`/`docker pull` asks for login even though the repo/package is supposed to be public | The visibility change wasn't confirmed all the way through on GitHub's side | Recheck `Settings → Danger Zone` (repo) or `Package settings` (package), redo the confirmation all the way to the end |

## Switching to Entra ID later

In `oauth2-proxy.cfg`, replace `provider = "oidc"` with `provider = "entra-id"` and point `oidc_issuer_url` to `https://login.microsoftonline.com/<tenant-id>/v2.0`, with the real Entra `client_id`/`client_secret` (the latter replaces the content of `secrets/oauth2_client_secret.txt`, same mechanics as step 5.7). `redirect_url` needs no attention here (already derived from `APP_DOMAIN`); only `allowed_groups` in this same file needs adjusting to the real group name on Entra ID's side.
